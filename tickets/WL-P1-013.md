# WL-P1-013: Decide how a new identity SQL function reaches existing V2 databases

## Goal

WL-P0-011I needs one new anonymous SQL gateway function that reports an invitation's
state from its token (`usable | expired | revoked | consumed`). The identity schema is
a frozen provider, so the function cannot be added to `0002_identity` without breaking
the checks that later revisions and existing databases rely on. The owner and an
Architect need to choose where the function lands and how the identity functions are
guarded afterwards, so that WL-P0-011I can be implemented.

## Context

What the code does today, read on 2026-11-12 at `af5ff8f`:

- `src/kurafolio/persistence/identity_schema.py` renders the `0002_identity` DDL: 21
  `wl_identity` gateway and operator functions plus `_clock_timestamp_v1`. Twenty of
  the 21 carry a `GUARD` that refuses to run unless `wl_pg.alembic_version` holds
  exactly `'0002_identity'`; `identity_status_v1` reports the revision instead.
- `source_schema.identity_replacements()` (`0003_source_lifecycle`) re-creates those
  functions with the guard rewritten to `'0003_source_lifecycle'`. It raises
  `Identity provider changed` unless it finds exactly 21 functions.
- `ingestion_schema.user_guard_ddl()` (`0004_ingestion`, provider in code, migration
  pending in WL-P0-007D) raises `Frozen identity guard changed` if the `0002` guard
  text changes.
- `migration._identity_target_inventory()` and `source_migration` verify the function
  names, signatures and bodies in an existing `0002` or `0003` database against the
  rendered DDL. Editing the `0002` text makes those databases fail verification.
- WL-P0-011E (user preferences) also needs new identity-side SQL and already plans a
  numbered migration coordinated with WL-P0-007D, which holds `migration-order`.
- WL-P0-011I's option 2 (split `registration_rejected` on submit) changes
  `register_commit_v1`'s body, so it meets the same constraint.

### Architect review, 2026-11-12 at `3b4a680`

Constraints the options above did not list:

- Every guarded function checks for one exact revision. The 21 identity functions
  check `'0003_source_lifecycle'` after `0003`; the `0003` source gateway functions
  (`source_schema.py`, the guard at about line 302) check the same value; the `0004`
  ingestion user guard checks `'0004_ingestion'`. So every new revision has to
  re-create all of them with its own revision in the guard, or they answer
  `instance_not_ready` once `alembic_version` moves.
- The `0004` provider code installs guards only for its new `wl_ingestion`
  functions; nothing in `ingestion_schema.py` re-creates the identity or source
  functions under `'0004_ingestion'` yet. The WL-P0-007 r7 SQL appendix ("Profile
  integration and readiness") does require the `0004` migration to replace those
  inherited guard literals, so this is covered by the gated spec. WL-P0-007D's
  acceptance criteria do not list it, which makes it easy to miss.
- A revision after `0004_ingestion` exists only on instances that run the explicit
  ingestion profile. `context.py:47` maps the default `identity` profile to `0002`
  and the `sources` profile to `0003`, so those instances never receive a function
  added in `0005`.
- Because each revision costs a full re-guard, options (a) and (b) need about the
  same work per revision. The real difference is that (a) ties WL-P0-011I to
  WL-P0-011E, which is in backlog with no gate approval and two open product
  decisions, behind WL-P0-007L (stale claim) and WL-P0-007D.
- Option (c) breaks the frozen-provider rule that `0003`, `0004` and the inventory
  checks enforce, and forces every existing `0002`/`0003` database to be recreated.
- A fourth option was put to the owner: add the revision as `0004` and renumber
  ingestion to `0005`. It would unblock WL-P0-011I sooner, but it changes the
  numbering under the gated WL-P0-007 r7 spec and the `migration-order` queue.

## Decisions needed

1. Where does `invite_status_v1` (anonymous, token digest in, one of four states out)
   land?
   - (a) A new numbered identity revision after `0004_ingestion`, shared with
     WL-P0-011E's preferences migration.
   - (b) A dedicated small revision after `0004_ingestion` for this function only.
   - (c) Treat V2 as unreleased and edit `0002_identity` in place.
   - (d) Add the revision as `0004` and renumber ingestion to `0005`.

### Owner decision recorded 2026-11-12

The owner chose **(b)**: a dedicated revision after `0004_ingestion`, used only for
`invite_status_v1` and the re-guards it requires. WL-P0-011E gets its own later
revision.

After the Architect review showed that `0005` reaches only ingestion-profile
instances, the owner confirmed (b) and chose a fallback: on `identity` (`0002`) and
`sources` (`0003`) instances, the registration page shows the form and keeps today's
combined `registration_rejected` message.

What this means for WL-P0-011I:

- Revision `0005_invite_status`, with `down_revision = "0004_ingestion"`, in
  `src/kurafolio/persistence/migrations/versions/0005_invite_status.py`. The DDL
  provider is a new module, `src/kurafolio/persistence/invite_status_schema.py`, with
  `REVISION` and `PREDECESSOR` constants like `ingestion_schema.py`.
- Guards stay exact-revision. The provider renders `CREATE OR REPLACE` copies of every
  function guarded at `'0004_ingestion'` with the guard rewritten to
  `'0005_invite_status'`, by text replacement from the frozen predecessor providers
  with exact-count checks, the way `source_schema.identity_replacements()` does.
  `invite_status_v1` uses the same guard. The `0002`, `0003` and `0004` text is not
  edited.
- Verification for `0002`, `0003` and `0004` databases stays as it is. New `0005`
  inventory checks cover the added function and its gateway grant.
- WL-P0-011I depends on WL-P0-007D, which supplies `0004_ingestion` and holds
  `migration-order`. WL-P0-011E's preferences revision comes after `0005`.
- On `identity` and `sources` instances the status check is unavailable and the page
  falls back to the current behaviour.
