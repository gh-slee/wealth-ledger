# WL-P1-013: Decide how a new identity SQL function reaches existing V2 databases

## Goal

WL-P0-011I needs one new anonymous SQL gateway function that reports an invitation's
state from its token (`usable | expired | revoked | consumed`). The identity schema is
a frozen provider, so the function cannot be added to `0002_identity` without breaking
the checks that later revisions and existing databases rely on. The owner and an
Architect need to choose where the function lands and how the identity functions are
guarded afterwards, so that WL-P0-011I can be implemented.

## Context

What the code does today, read on 2026-11-12 at `af5ff8f`:

- `src/kurafolio/persistence/identity_schema.py` renders the `0002_identity` DDL: 21
  `wl_identity` gateway and operator functions plus `_clock_timestamp_v1`. Each
  function's `GUARD` refuses to run unless `wl_pg.alembic_version` holds exactly
  `'0002_identity'`.
- `source_schema.identity_replacements()` (`0003_source_lifecycle`) re-creates those
  functions with the guard rewritten to `'0003_source_lifecycle'`. It raises
  `Identity provider changed` unless it finds exactly 21 functions.
- `ingestion_schema.user_guard_ddl()` (`0004_ingestion`, provider in code, migration
  pending in WL-P0-007D) raises `Frozen identity guard changed` if the `0002` guard
  text changes.
- `migration._identity_target_inventory()` and `source_migration` verify the function
  names, signatures and bodies in an existing `0002` or `0003` database against the
  rendered DDL. Editing the `0002` text makes those databases fail verification.
- WL-P0-011E (user preferences) also needs new identity-side SQL and already plans a
  numbered migration coordinated with WL-P0-007D, which holds `migration-order`.
- WL-P0-011I's option 2 (split `registration_rejected` on submit) changes
  `register_commit_v1`'s body, so it meets the same constraint.

## Decisions needed

1. Where does `invite_status_v1` (anonymous, token digest in, one of four states out)
   land?
   - (a) A new numbered identity revision after `0004_ingestion`, shared with
     WL-P0-011E's preferences migration. It adds the function, re-guards the identity
     functions for the new revision and extends the inventory checks. One migration
     instead of two; WL-P0-011I then waits on WL-P0-007D and that migration.
   - (b) A dedicated small revision after `0004_ingestion` for this function only.
     Smaller review, but a second identity revision next to WL-P0-011E's.
   - (c) Treat V2 as unreleased and edit `0002_identity` in place, updating the
     function count in `0003`, the frozen-guard check in `0004` and the inventories.
     No new revision, but every existing `0002`/`0003` database must be recreated,
     and it breaks the frozen-provider rule the later revisions enforce.
   - Recommendation: (a). It follows the frozen-provider rule, keeps the migration
     count down and already has an owner in the `migration-order` queue.
