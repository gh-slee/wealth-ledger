# WL-P1-010: Make CI faster and cheaper for many parallel agent branches

## Goal

Agents are told to push work-in-progress commits at every checkpoint, and each push to a branch with an open pull request starts the seven-job pipeline twice. The longest job finishes within a minute of its timeout. With several agents working at once, CI will queue, time out and slow every merge.

## Context

### Current behaviour

- `.github/workflows/ci.yml` triggers on every `push` and every `pull_request` with no branch filter and no `concurrency` group. Run history on 2026-11-09 shows pairs of runs for the same commit, one per trigger.
- The last run on `main` took 24 minutes 10 seconds for `python-312-linux` against a 25-minute timeout, 17 minutes for `parser-sdk-packages`, and 2 to 5 minutes for the other five jobs.
- A change that touches only `tickets/` or `docs/` runs every job, including the PostgreSQL and Docker suites.
- When the browser job fails it prints the first error contexts; no report or screenshot is kept.
- `main` has no branch protection (GitHub API, 2026-11-10), so required checks are a convention.

### Expected behaviour

- One run per pull-request commit; a newer commit cancels the older run of the same branch. `main` still runs on push.
- The unit-test job has real headroom: split into two or more parallel jobs or shards, each well under its timeout.
- A change limited to `tickets/` and Markdown under `docs/` runs the language, publication and ticket checks only, and still reports one status a required check can point at.
- A failed browser job keeps its Playwright report as an artifact.

### Scope

- In scope: triggers, concurrency, job splitting, path-based skipping with one always-reported summary job, artifact upload.
- Out of scope: new test suites (WL-P0-022, WL-P0-023), the local pre-PR image gate, branch protection settings (owner action, see Decisions needed).

### Implementation notes

- Use `concurrency: group: ${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress` for pull requests only.
- Path filtering must never skip a job for a change that touches `src/`, `tests/`, `scripts/`, `frontend/`, lock files, Docker files or the workflow itself. When in doubt, run everything.
- Splitting `unittest discover` needs a deterministic partition (for example by file-name pattern); prove the union equals today's test count.
- Keep actions pinned by commit and `permissions: contents: read`.

## Acceptance criteria

- [ ] Given two pushes to a pull-request branch one minute apart, then the first run is cancelled and one run reports on the latest commit.
- [ ] Given a push to a branch with an open pull request, then one pipeline runs, not two.
- [ ] Given a pull request that changes only a ticket file, then the heavy jobs are skipped, the summary status is green and it took under five minutes.
- [ ] Given a pull request that changes one file under `src/`, then every job runs.
- [ ] The number of unit tests executed across the split jobs equals the number before the split; each job ends with at least 30% of its timeout unused.
- [ ] A deliberately failing browser test produces a downloadable report.

### Tests

- Demonstration pull requests for the ticket-only and source-change cases, linked in the PR.
- A check that compares executed test counts before and after the split.

## Plan

- [ ] Triggers and concurrency.
- [ ] Split the unit-test job.
- [ ] Path-based skipping with a summary job.
- [ ] Artifact upload.
- [ ] Documentation in `docs/development.md`.

## Decisions needed

1. Skip heavy jobs for ticket-only and docs-only changes. Options: (a) yes, with a summary job; (b) always run everything. Recommendation: (a).
2. Branch protection on `main` with the summary check required. This is a repository setting only the owner can change. Recommendation: enable it, so "CI passed" is enforced and not a convention.
