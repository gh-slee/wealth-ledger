# WL-P0-022: Run the ingestion PostgreSQL acceptance tests in CI and fail on unexpected skips

## Goal

The real-SQL tests for the V2 import functions never run in CI. They are the only automated proof of exactly-once booking, fencing and cleanup, and the MVP's import tickets are about to change that SQL. Today a pull request can break them and stay green, and a reviewer has only the author's word that they were run locally.

## Context

### Current behaviour

- `tests/test_postgres_migration.py:230` gates `IngestionAppendOnlyPostgresTests` (93 test methods) on `KURAFOLIO_INGESTION_TEST=1`.
- `.github/workflows/ci.yml` never sets that variable (verified by search on 2026-11-10). The `postgres-foundation` job runs `test_postgres_*.py` with `KURAFOLIO_PG_TEST=1` only, so those 93 tests are reported as skipped in every run.
- The test starts its own PostgreSQL container with `--pull never` using the image pinned in `IngestionAppendOnlyPostgresTests.IMAGE`; the image must be present first ([web-v2-imports.md](../docs/web-v2-imports.md), "optional storage-fragment check").
- A skipped test leaves the job green. Nothing checks that a job which exists to run gated tests actually ran them.

### Expected behaviour

- A CI job pulls the pinned image, sets `KURAFOLIO_INGESTION_TEST=1` and runs `test_postgres_migration.py`. It fails if any ingestion test fails.
- Each job whose purpose is a gated suite fails when that suite reports skips it did not expect, so a missing variable can never again pass silently.
- Pull requests that touch `src/kurafolio/persistence/ingestion_schema.py` cannot merge green without these tests having run.

### Scope

- In scope: the workflow job, a small skip-guard script, a line in `docs/development.md` and `docs/web-v2-imports.md`.
- Out of scope: changing the tests themselves, speeding up CI (WL-P1-010), a V2 browser suite (WL-P0-023).

### Implementation notes

- Model the job on `postgres-foundation` in the workflow. Pull the exact digest from the test module instead of repeating it in YAML, so the two cannot drift.
- Skip guard: run unittest with a result class or parse `-v` output and compare the skipped count with an expected number given on the command line; standard library only, under `scripts/`.
- Apply the guard to `postgres-foundation`, `postgres-identity`, `postgres-sources`, `docker-foundation` and the new job, each with its own expected count.
- Keep action references pinned by commit as the workflow already does, and `permissions: contents: read`.

## Acceptance criteria

- [x] Given a pull request, then a CI job runs the ingestion tests (93 when filed, 103 now) with 0 skipped and reports their result.
- [x] Given the variable is removed from the job, then the job fails on the skip guard instead of passing.
- [x] Given a deliberately broken SQL fragment on a test branch, then the job fails (show the run link in the PR, then revert).
- [x] Existing jobs keep their results; the guard reports their current skip counts and fails on a change.
- [x] The job finishes inside its timeout with margin; its duration is recorded in the PR.
