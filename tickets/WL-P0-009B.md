# WL-P0-009B: Store market prices in PostgreSQL and refresh them on a schedule and on demand

## Goal

The owner wants the values on the analysis pages to follow the market: the app fetches prices at intervals and when the user presses Refresh, for any security a user holds. WL-P0-009A gives the adapter that fetches one quote. Nothing stores quotes, decides what to fetch, runs on a timer or lets the pages read the latest price. This ticket adds that.

## Context

### Current behaviour

- After the MVP, securities are valued from the market values inside the imported file and Bitcoin from a price fetched at request time (WL-P0-012A, first version). Nothing refreshes without a new import.
- The existing fetchers write JSON files under a project directory (`src/wealth_ledger/prices.py:78-100`, `src/wealth_ledger/fx.py:71`). V2 has no project directory; its data is in PostgreSQL.
- The V2 worker (WL-P0-007F) is dedicated to imports and started by a trusted launcher. It is not a general scheduler.
- The Stock/Bond toolbar already has a Refresh button that expects "the market refresh route" (WL-P0-012B).

### Expected behaviour

- A market reference store in PostgreSQL: one row per listing (exchange plus symbol, or a crypto pair) and observation time, holding price, currency, source name, delay class, "as of" time, fetch time and a hash of the bounded evidence. Rows are shared by all users because they are public market data; they hold no user identifier.
- The set to refresh is derived from what users currently hold (WL-P0-008 positions). No hard-coded symbol list.
- A refresh process runs on a timer and fetches each needed listing once per interval, whatever the number of users holding it.
- `POST /api/v2/market/refresh` asks for a refresh now. Several requests while one is running join the running one. A user cannot trigger more than one upstream round per minimum interval; an earlier request answers with the time of the last check.
- `GET /api/v2/market/status` returns, for the signed-in user's holdings, the latest "as of" time, the last check time, whether a refresh is running, and the listings that have no price with a reason.
- The analysis responses (WL-P0-012A) use the latest stored price for each holding when one exists, and fall back to the imported market value marked with its import date when none does. A price change creates a new calculation generation; the fact generation and all quantities stay the same.
- A failed or empty fetch keeps the last valid price, marked stale with its time. Nothing becomes zero.

### Defaults approved by the owner on 2026-11-11

| Setting | Default | Reason |
|---|---|---|
| Bitcoin interval | 5 minutes | The public exchange API is real time and has a generous limit |
| Securities interval | 15 minutes, only while the listing's exchange is open; one fetch after the close | Free sources are 15 minutes delayed or end of day; fetching more often changes nothing |
| Minimum time between manual refreshes | 60 seconds per instance | Protects the provider budget when several users press Refresh |
| When no user has signed in for 24 hours | Refresh once a day | An idle instance should not spend the provider budget |

The operator can change each value in configuration. The intervals never go below the provider's licensed delay.

### Scope

- In scope: the store and its migration, the refresh process and its command, the two routes, the wiring into the analysis service, configuration, tests, operator documentation.
- Out of scope: FX rates and the currency list (WL-P0-009C), historical backfill and the daily curve (WL-P0-009D), an official keyed provider (WL-P0-009E), ETF holdings (WL-P0-010A), any page change beyond what WL-P0-012B already expects.

### Implementation notes

- Add the tables as a new numbered migration after the last one on `main`; read [postgres-foundation.md](../docs/postgres-foundation.md) and `src/wealth_ledger/persistence/` for the migration and role conventions. The store is not tenant data, so decide and document its row-level-security policy: readable by the runtime role, writable only by the refresh process role.
- Planning judgement, to confirm in the PR: run refresh as its own process (`python -m wealth_ledger.web_v2 refresh-market`, a third service in the WL-P0-021 compose file) and do not extend the import worker. Coordinate a single runner with a PostgreSQL advisory lock or lease so two processes never fetch the same round.
- Use the claim's `isolation_id` and `port_base` for every database and container.
- Exchange hours: keep a small table of trading sessions for the exchanges the built-in sources produce (Toronto, New York, Nasdaq); an unknown exchange is refreshed on the interval all day.
- `Decimal` only. A listing is exchange plus symbol; a bare ticker is ambiguous (WL-P0-009A).
- Corporate actions: when the stored quantity predates a split and the fetched price is after it, the value would show a false loss. If the provider reports a split or the price moves by a factor consistent with one between two closes, mark the holding "needs a newer import" and exclude it from `complete_total`; never apply an adjustment the source did not confirm (golden case G19).

## Acceptance criteria

- [ ] Given the fake provider and one user holding two listings, when the refresh process runs once, then one row per listing is stored with price, currency, "as of", fetch time, source and delay class.
- [ ] Given two users holding the same listing, when a round runs, then one upstream request is made for it.
- [ ] Given no new import, when the Bitcoin price changes from USD 60,000 to 61,000 at the same FX rate, then the crypto and total values rise by the oracle amount, quantities and fact generation are unchanged and the calculation generation is new (golden case G10).
- [ ] Given a listing whose fetch fails, then its last valid price is used, the row is marked stale with its time, and `/market/status` lists it with a reason.
- [ ] Given a holding that never had a fetched price, then its value comes from the import with the import date, and if there is neither, `complete_total` is null and `known_subtotal` excludes it (golden case G09).
- [ ] Given three refresh requests within the minimum interval, then one upstream round runs and all three responses report the same check time.
- [ ] Given two refresh processes started at once, then only one fetches.
- [ ] Given a split-consistent price jump with an older quantity, then the holding is marked unresolved and is not valued at the misleading price.
- [ ] Given user A, then `/market/status` lists only listings A holds.
- [ ] The operator guide documents the command, the settings and their defaults.
