# WL-P1-007: Define a configurable time zone for display and month grouping

## Goal

Every time on screen and in reports is shown in America/Toronto, and monthly Bitcoin tables group orders by Toronto month. That suits one household and is wrong for any user elsewhere, including a TWD-reporting user the product already supports. WL-P0-011E adds a per-user time zone preference for V2, but nothing defines what that zone changes. Produce a reviewed contract for where a time zone setting applies and where history must stay as recorded, then file the implementation tickets.

## Context

### Current behaviour (verified in source)

- Display: `frontend/src/lib/format.ts:52` and `frontend/src/components/chart-view.tsx:115` hard-code `America/Toronto`; the header text "All displayed times: Toronto" is a catalog string.
- Core: `src/wealth_ledger/workflow.py:16` (`LOCAL`), `formatting.py:42`, `wallet_reports.py:35`, `web/exports.py:54`, `publishing.py:27,212`, `reporting.py:142` and the month bucket in `source_presentation.py:162`.
- Saved editions are frozen. Their text and month groups must not be recomputed.

### Scope

- In scope: a written contract answering the questions under Decisions needed; an inventory of each hard-coded use classified as display, grouping or file naming; follow-up tickets for the current frontend and for V2 (WL-P0-012, WL-P0-013).
- Out of scope: any code change in this ticket.

## Acceptance criteria

- [ ] The contract states how frozen editions, fingerprints and existing CSV/JSON exports stay byte-identical.
- [ ] The owner has answered each decision; answers are recorded in the Log.
- [ ] Follow-up tickets exist with acceptance criteria that name a zone east of UTC and one west of it as test cases.

## Plan

- [ ] Inventory and classify.
- [ ] Draft the contract and the decision options.
- [ ] Owner review; file follow-ups.

## Decisions needed

1. Scope of the setting. Options: (a) display only, month grouping stays in the instance zone; (b) display and grouping per user; (c) one instance-wide zone chosen at setup. Recommendation: (c) for the current SQLite app because it needs no per-user state, and (b) for V2 where the profile already carries locale and currency.
2. Month grouping of existing data when the zone changes. Options: keep saved editions as recorded and apply the new zone only to later calculations, or refuse to change the zone after the first import. Recommendation: the first, with the zone recorded in each calculation.
3. Default for new installations. Options: UTC, or the browser zone at first setup. Recommendation: browser zone at first setup, stored explicitly.
