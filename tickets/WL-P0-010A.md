# WL-P0-010A: Store official ETF holdings in PostgreSQL and refresh them for held funds

## Goal

To show what a user really owns through their ETFs, V2 needs each fund's underlying holdings from the issuer, kept current without the user doing anything. The shipped application already downloads and parses them, but saves them as files in a project directory and only when a report is built. Move that into the V2 reference store and refresh it automatically for every fund a user holds.

## Context

### Current behaviour

- `src/kurafolio/fund_sources.py` downloads public issuer files and parses them. Its `REGISTRY` (lines 23-40) lists eight funds from seven issuers, each with an adapter, a URL and a maximum age in days. `fetch_fund` (line 323) writes into a directory.
- `src/kurafolio/lookthrough.py` resolves funds inside funds and matches company identities (`Identities`, line 57; `calculate`, line 126).
- A fund that is not in the registry has no holdings; the shipped page reports it as unsupported.
- WL-P0-009B adds a shared market reference store and a refresh process.

### Expected behaviour

- A fund holdings store in PostgreSQL: per fund listing and effective date, the list of constituents with name, weight, asset kind, country, identifiers and child fund reference; plus issuer, source URL, effective date, fetch time, content hash and parser version. Rows are public reference data shared by all users.
- The refresh process fetches holdings for every registered fund that at least one user holds, when the stored copy is older than that fund's maximum age, and once when a fund is first held.
- A new download replaces nothing: each effective date is kept, and the latest valid one is current.
- A failed download or a file that fails validation keeps the previous copy, marked stale with its date and the reason.
- A held fund that is not in the registry is recorded as "no official source configured"; it is never fetched from an unofficial page and never given invented holdings.
- A service function returns, for a set of fund listings, the current holdings with their dates and status. WL-P0-010B is its only consumer in this epic.
- `GET /api/v2/reference/funds` returns, for the signed-in user's held funds: issuer, effective date, fetch time, status (current, stale, unsupported, failed) and the number of constituents.

### Scope

- In scope: the store and migration, porting the fetch and parse path to write to it, automatic refresh, the status route, tests, operator documentation.
- Out of scope: the exposure calculation and its endpoint (WL-P0-010B), funds a user does not hold and search (WL-P1-002), adding issuers or funds to the registry (a normal contribution after WL-P1-003), the page (WL-P0-012E).

### Implementation notes

- Port, do not rewrite, the parsers and their validation; `tests/test_lookthrough.py` and the parser tests hold their expected values. Keep `VERSION` semantics: a parser change is a new parser version on new rows.
- The module's rule "never submit portfolio data" stays: requests carry no user data, and the set of funds fetched is the union over users.
- Fund identity is exchange plus symbol as in the registry keys (`XTSE:VEQT`); map from the position's listing (WL-P0-008).
- Use the lease from WL-P0-009B so two processes do not download the same file.
- Tests use saved synthetic issuer files; no network.
- Add the tables as a new numbered migration after the last one on `main`; state the row-level-security policy as in WL-P0-009B.

## Acceptance criteria

- [ ] Given a user who holds a registered fund with no stored holdings, when the refresh process runs, then the holdings are stored with issuer, effective date, fetch time, hash and parser version.
- [ ] Given a stored copy younger than the fund's maximum age, then no download happens.
- [ ] Given a newer effective date from the issuer, then both dates exist and the newer one is current.
- [ ] Given a download error or an invalid file, then the previous copy stays current and is marked stale with the reason.
- [ ] Given a held fund that is not in the registry, then its status is unsupported and no request is made for it.
- [ ] Given two users holding the same fund, then one download happens.
- [ ] Given a fund no user holds any more, then it is no longer refreshed and its stored rows remain.
- [ ] Given user A, then the status route lists only funds A holds.
- [ ] The existing parser and look-through tests still pass unchanged.
