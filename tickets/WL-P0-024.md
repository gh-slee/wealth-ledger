# WL-P0-024: Rename the project to Kurafolio everywhere, before parallel V2 work starts

## Goal

The owner chose the name Kurafolio on 2026-11-11: kura (the kanji U+8535) is the Japanese storehouse where a family kept its valuables, joined to "folio" for portfolio. The rename covers the GitHub repository, every file in it and the checkout folder on the owner's computer. It touches about 290 files, so it must be merged before several agents open branches, or every one of them would have to rebase across it. The owner decided on 2026-11-11 that it runs first and alone.

### Owner decisions recorded 2026-11-11

- Scope: everything. Repository, documentation, UI text, Python package, console scripts, image and compose names, environment variables and the local folder.
- No aliases: the old names stop working. The owner updates the configuration of their running instance by hand, following a note this ticket writes.
- Timing: before the MVP tickets. The six tickets that were claimable depend on this one.
- Name: Kurafolio. The forms are `kurafolio` (Python package, distribution, image, repository), `KURAFOLIO_` (environment variables), `Kurafolio` (prose and UI) and `kurafolio-` (console scripts, agent skill folders, the frontend package).
- The README explains the name.

### Expected behaviour

- Every form in the table uses the new name in the matching style: `wealth_ledger` and `wealth-ledger` become `kurafolio`, `WEALTH_LEDGER` becomes `KURAFOLIO`, `Wealth Ledger` and `WealthLedger` become `Kurafolio`, `wealthledger-` becomes `kurafolio-`.
- The README has a short section near the top, "Why Kurafolio", that says: kura (the kanji U+8535) is the traditional Japanese storehouse where a family kept its valuables; Kurafolio is that storehouse for your portfolio, kept on your own machine. Two or three sentences, with the character shown. The same sentence is the repository description on GitHub.
- The GitHub repository is renamed. GitHub redirects the old URL; links in the repository use the new one.
- All checks pass under the new name: the full test suite, the frontend build and tests, CI, and `scripts/check_pr_image.py`.
- A short upgrade note in the README tells an existing operator exactly what to change: environment variable names, image name, console script names, compose project name, and how to keep using their existing data volume.

### What must not change

- Data already stored: database contents, saved report editions and their manifests, backup files, evidence hashes and any identifier written inside them. [AGENTS.md](../AGENTS.md) forbids rewriting old manifests. Code that reads an old identifier from stored data keeps accepting it; that is reading history, not an alias.
- Public contract strings whose change would break stored data or installed plugins: parser protocol identifiers, schema and format version strings, plugin entry-point group names, migration names. List each one found and keep it, with a comment saying why.
- Ticket IDs. `WL-` stays; renaming a hundred files and every cross-reference buys nothing.
- Git history. No rewrite, no force-push.
- Licence and third-party notices, except the project's own name.

### Scope

- In scope: the rename in the repository, the GitHub repository rename, the local folder rename with worktree repair, the upgrade note, updating README screenshots only if they show the old name.
- Out of scope: a logo or visual identity, a domain, publishing a package or image under the new name, changing the owner's running instance.

### Implementation notes

- Do it in separate commits by form so the diff can be reviewed: package directory move (`git mv`) and imports; distribution, scripts and images; environment variables; prose and UI text; agent skill folders. Run the focused tests after each.
- Search for the name split across lines, in generated files (`frontend` generated API types, lock files) and in test expectations of user-visible text in the three locales.
- Docker volume names: a compose project rename changes default volume names, which would make an existing instance start empty. Either keep explicit volume names in `compose.yaml` or put the exact migration steps in the upgrade note. Never touch a real volume.
- CI workflow names, job names and the test switches change together; a missed switch silently skips tests (see WL-P0-022).
- GitHub: `gh repo rename kurafolio --repo gh-slee/wealth-ledger`, then `gh repo edit --description`. The owner asked for this on 2026-11-11; do it only after the rename PR is merged, then update the `origin` URL.
- Local folder: after the merge and with no other agent session running, the owner's checkout folder is renamed and `git worktree repair` is run for every listed worktree (22 on 2026-11-11; remove finished ones first with the owner's agreement). Tool state keyed to the old path (editor workspaces, agent memory directories, virtual environments with absolute paths) does not follow; list what was found and recreate `.venv`. If the agent's own session runs inside that folder, it prepares a script and the owner runs it.
- Before the PR, check that no other branch has unmerged work the owner wants to keep; list open branches and worktrees in the PR.
