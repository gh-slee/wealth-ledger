# WL-P0-023: Add a real V2 end-to-end browser suite and its CI job

## Goal

Every V2 screen ticket tests against mocked `/api/v2` responses, so nothing proves that the browser, the V2 API, PostgreSQL and the import worker work together. The existing browser suite covers only the SQLite application. Before the owner uses the MVP for real, one automated run must walk the owner's flow on a real V2 stack and keep doing so on every pull request.

## Context

### Current behaviour

- `frontend/tests/browser/` holds six specs with 25 tests, all against the SQLite fixture started by `scripts/web_browser_fixture.py` (`frontend/playwright.config.ts`).
- The `browser-workflow` CI job runs them; no CI job starts a V2 stack with a browser.
- V2 screen tickets (WL-P0-011A to D, 012B to D) specify `page.route` mocks.
- The shipped fixture holds one observation per portfolio, which is how a chart defect with a single data point went unnoticed (UX-P1-011).

### Expected behaviour

- A disposable V2 fixture: PostgreSQL with migrations applied, the V2 API serving the bundle, the import worker, one administrator and synthetic source files. It starts and tears down with one command and never touches an existing instance.
- A Playwright project `v2` with its own spec directory, run by its own CI job.
- First journey: accept an invitation, sign in, enable a plugin, import the example holdings file, see the Stock/Bond value. Journeys for the exchange file, Crypto, Total and currency switching are added as their pages land.
- Fixture data varies: at least two imports on different dates, two users, and an account that disappears between imports.

### Scope

- In scope: the fixture script, the Playwright project, the first journey, the CI job, documentation.
- Out of scope: replacing the mocked specs (they stay as fast component-level checks), deployment (WL-P0-021), load testing.

### Implementation notes

- Reuse `scripts/postgres.py test-identity-environment` and its cleanup command for the database, as the `postgres-identity` CI job does.
- Port selection must honour `KURAFOLIO_E2E_PORT` (WL-P0-018) and the claim's `port_base`.
- Only invented data. The example files under `examples/data/` are the inputs.
- Each later V2 page ticket adds its real journey here once its page exists; say so in that ticket's Handoff when you finish this one.
- Upload the Playwright report as a CI artifact on failure; it contains synthetic data only.

## Acceptance criteria

- [ ] Given a clean checkout with Docker, when the documented command runs, then the V2 fixture starts, the first journey passes and every container and volume it created is removed.
- [ ] Given two users in the fixture, then a test proves user B cannot see user A's holdings through the browser.
- [ ] Given a second import that lacks an account, then the review step asks to keep or close it (WL-P0-011D) and the test covers both answers.
- [ ] The CI job runs on every pull request, finishes inside its timeout and uploads the report on failure.
- [ ] The existing SQLite browser suite still passes unchanged.

### Tests

- The suite is the test. Add one deliberately failing assertion on a branch to prove the job fails, then remove it.
