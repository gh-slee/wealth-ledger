# UX-P1-013: Replace typed ISO timestamps with date, time and zone controls

## Goal

The import form and the financial-records forms ask the user to type timestamps such as `2026-10-17T18:00:00-04:00`. Most people do not know their UTC offset on a past date, and a wrong offset silently moves an observation. Let the user pick a date and a time and choose a named zone; the form builds the offset timestamp and shows it before preview.

## Context

### Current behaviour

- Observed on the synthetic browser fixture on 2026-11-10: the import form has two text fields with the placeholder `2026-10-17T18:00:00-04:00` ("Valuation time (optional, with UTC offset)", "Balance observed at (with UTC offset)").
- `frontend/src/components/imports.tsx:507` (`as_of`) and `:521` (`observed`) are plain `<input>` elements.
- `frontend/src/components/financial.tsx` uses the same convention for declaration timestamps.
- `frontend/src/components/report-exports.tsx:93,97` already uses native `type="date"` inputs.

### Expected behaviour

- One shared field: date, time, zone select defaulting to the browser zone, and a read-only line showing the resulting offset timestamp.
- A local time that does not exist (daylight-saving gap) gives an inline error and disables preview; an ambiguous one asks which offset.
- An "enter exactly" text fallback stays under the existing advanced disclosure.

### Scope

- In scope: the shared component; its use in the import form and every declaration form.
- Out of scope: API changes, how the server interprets time, the display zone of saved reports (WL-P1-007), V2 import screens (WL-P0-011D).
- Non-goals: a date-picker dependency. Native inputs and `Intl` are enough.

### Implementation notes

- Keep field `name` attributes and request bodies unchanged so `frontend/tests/browser/workflow.spec.ts` and `import-review.spec.ts` need only input changes.
- Unsent values must stay in the tab after an error, as today.
- Compute the offset with `Intl.DateTimeFormat` and `timeZoneName: "longOffset"`; unit-test it.

## Acceptance criteria

- [ ] Given the import form, when the user picks 2026-10-17, 18:00 and America/Toronto, then the request carries `2026-10-17T18:00:00-04:00` and that string is shown before submit.
- [ ] Given a local time skipped by a daylight-saving change, when the user leaves the field, then an inline error names the problem and preview is disabled.
- [ ] Given an ambiguous local time, then the user must choose one of the two offsets before preview.
- [ ] Given the declaration forms in Financial records, then every timestamp uses the same component.
- [ ] Each control has a programmatic label, the group works by keyboard alone and errors are linked with `aria-describedby`.
- [ ] The three locales pass; the existing dated-BTC-total browser test passes.

### Tests

- Unit tests for normal, skipped and ambiguous times in zones east and west of UTC.
- Update the two browser specs to use the controls.
