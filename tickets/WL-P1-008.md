# WL-P1-008: Add a board drift and readiness check to the ticket script

## Goal

The board on `main` disagrees with Git in ways `tickets.py check` cannot see, and tickets can be marked `ready` without the content an agent needs. An agent reading the board today is told three tickets are ready when none can be claimed, and two merged tickets still read `in_review`. Add a `doctor` command that reports these cases and a short definition of ready that it enforces, so the owner and agents can trust the board.

## Context

### Evidence (2026-11-09)

- WL-P0-017 (PR #30) and WL-P0-018 (PR #34) are merged; both read `in_review` on `main`. Closing WL-P0-007A/B/I needed a separate PR (#36), and another is open for 018 (#37).
- WL-P0-011, WL-P0-011A and WL-P0-016 are `ready` with `gate: owner` and an empty `gate_approval`, so `next` never offers them.
- Thirty-eight tickets set `spec:` to a path under `docs/specs/`, which is untracked until WL-P0-016. In a fresh clone those links do not resolve.
- `tickets/ROADMAP.md` (updated 2026-11-05) still describes WL-P0-007A as uncommitted.
- Thirty-six tickets carry the placeholder Handoff "Claim the ticket, read the linked docs and start the first Plan item"; 38 of the 46 open tickets say "Verify: Not applicable yet"; 7 of the 46 name a source path.

### Scope

- In scope: `python3 scripts/tickets.py doctor`, read-only, exit code 1 on findings; a "Definition of ready" section in `tickets/README.md`; tests in `tests/test_tickets.py`.
- Out of scope: changing any ticket's status, the front-matter schema, the claim protocol, or making `check` stricter (it runs in the test suite and must keep passing on today's board).
- Non-goals: calling GitHub. Use local Git refs only so the command works offline and in sandboxes.

### Checks to implement

1. `status: ready` with `gate: owner` and no `gate_approval`.
2. `status` in `in_progress`, `in_review` or `ready` while the ticket's `branch` is an ancestor of `origin/main`.
3. `spec:` or a relative Markdown link in the body that does not resolve to a tracked file.
4. `status: ready` where Handoff `Verify` is "Not applicable yet", the Plan has fewer than two steps, or the body names no existing repository path.
5. A stale claim (older than `WL_TICKET_STALE_MINUTES`) on a ticket whose status is `done`.
6. An epic whose Plan omits a child ticket that names it as `parent`.

## Acceptance criteria
