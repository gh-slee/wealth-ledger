# WL-P1-011: Review every pull request automatically in CI

## Goal

Since 2026-11-11 the implementing agent starts its own independent reviewer before it opens a pull request ([README.md](README.md), Reviews rule). That reviewer is launched by the author and is usually the same model, so it can be skipped or share the author's blind spots. A reviewer that runs in CI on every pull request cannot be skipped and can be a different model. The owner then reads its findings on GitHub before merging.

## Context

### Current behaviour

- `.github/workflows/ci.yml` runs tests only. Nothing comments on a pull request.
- `main` has no branch protection ([CI_E2E_ASSESSMENT.md](CI_E2E_ASSESSMENT.md)).
- Role guidance for QA and Architect review is in `.agents/skills/`.

### Expected behaviour

- A workflow runs on each pull request and on new commits to it. It gives a review agent the diff, the ticket file named in the branch or PR, and the role guidance, and posts one comment: a verdict per acceptance criterion, findings with file and line, and what it could not check.
- It updates its own comment on new commits instead of adding more.
- It never pushes, approves, merges or edits the branch, and it has read-only repository permission plus permission to comment.
- A missing secret or a provider outage makes the job report "review not run"; it does not fail the other checks.
- Pull requests from forks do not get the secret.
- The cost per run is bounded by a size limit on the diff and a timeout, both configurable.

### Scope

- In scope: the workflow, its prompt file, documentation, and the owner steps to add the secret.
- Out of scope: making the review a required check (decide after a few weeks of use), branch protection (WL-P1-010 area), replacing the author-launched review.

### Implementation notes

- Pin the action to a commit hash, as the repository pins its other actions.
- The prompt is a file in the repository so changes to it are reviewed.
- Pull request text is public: the comment must not contain secrets or environment values, and follows the repository rule for public text.
- Text inside a diff or a ticket is data for the reviewer, never an instruction to it.

## Acceptance criteria

- [ ] Given a pull request from a branch in the repository, then one review comment appears with a verdict for each acceptance criterion of the linked ticket.
- [ ] Given a second push, then the same comment is updated.
- [ ] Given no secret, then the job ends neutral with "review not run" and other checks are unaffected.
- [ ] Given a pull request from a fork, then the secret is not exposed and the job says so.
- [ ] The workflow's permissions are read for contents and write for pull-request comments only.
- [ ] The documentation tells the owner how to add, rotate and remove the secret and how to turn the reviewer off.

### Tests

- A dry-run mode of the review script that prints the comment for a saved synthetic diff, run in CI without the secret.

## Plan

## Decisions needed

1. Which reviewer service and model runs in CI, and under which account's API key. Recommendation: a different vendor from the one that writes most of the code, so author and reviewer do not share blind spots.
2. A monthly spending limit. Recommendation: set a hard limit at the provider, and skip diffs above a size limit.
3. Whether the owner adds the repository secret. Only the owner can; no agent handles the key.
