# WL-P1-012: Fix the timing race in the regular parser upload browser test

## Goal

One browser test fails now and then for reasons unrelated to the change under test. With several agents opening pull requests, each false failure costs a rerun and teaches agents to distrust CI. Make the test deterministic.

## Context

### Current behaviour

- On 2026-11-11 the same commit ran CI twice. `browser-workflow` passed in one run and failed in the other; the commit changed Markdown only.
- The failure: `frontend/tests/browser/workflow.spec.ts:676`, "regular parser upload reviews mappings and publishes without hand-written contexts". Line 728 expects an alert containing `request_failed` within 5 seconds and no alert appears.
- The test's own comment at line 729 says the worker may finish before the retry, so the step depends on which of two things happens first.

### Expected behaviour

- The test makes the failed request happen for certain (for example by intercepting that one request with the browser test tool) instead of relying on timing, then checks the alert and the retry.
- No change to what the test proves about the page.

### Scope

- In scope: this test, and any other step in the same file that depends on worker timing in the same way.
- Out of scope: retries for the whole suite, product code, the V2 suite (WL-P0-023).

## Acceptance criteria

- [ ] The test passes 30 times in a row locally or in a CI loop, with the count recorded in the PR.
- [ ] The test still fails if the alert is removed from the page.
- [ ] No global retry or longer global timeout is added to hide the race.

### Tests

- `npm --prefix frontend run test:e2e`

## Plan

- [ ] Reproduce by running the test in a loop.
- [ ] Make the failed request deterministic.
- [ ] Loop to confirm.
