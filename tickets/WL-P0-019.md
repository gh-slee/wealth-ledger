# WL-P0-019: Decide the V2 delivery order and the hardening scope of the first release

## Goal

V2 exists to give users a simpler flow: register, enable sources, import, see current analysis ([ROADMAP.md](ROADMAP.md)). Every V2 change merged so far is backend foundation that no user can reach. The remaining path to the first visible V2 screen with real data runs through about fifteen tickets, most of them frontier-tier with high or critical risk, each with an owner gate and an independent review. The owner chooses whether to keep that order or to reach a thin end-to-end slice first and harden afterwards.

## Context

- Inventory, coverage and batches: [UX_FEATURE_INVENTORY.md](UX_FEATURE_INVENTORY.md), [TICKET_CHANGES.md](TICKET_CHANGES.md).
- Board evidence on 2026-11-10: `python3 scripts/tickets.py next --tier frontier` lists no claimable ticket. WL-P0-007C, WL-P0-007J and WL-P0-009 are blocked on decisions; WL-P0-011, WL-P0-011A and WL-P0-016 read `ready` but have no `gate_approval`.
- Merged V2 surface: PostgreSQL foundation, identity backend, source lifecycle, and the ingestion SQL in `src/wealth_ledger/persistence/ingestion_schema.py` (4,256 lines). [capability-status.md](../docs/capability-status.md) states that none of it is an operational import service.
- The r7 ingestion contract was written for hostile multi-tenant load: shared rate buckets (WL-P0-007J), per-user raw slots (WL-P0-007K), cleanup leases (WL-P0-007C) and Linux parser containment (WL-P0-007F). The approved registration default is invite-only on a self-hosted instance (OD-01 recommendation).
- This ticket changes no approved decision by itself. D01 to D14 stay as approved. It asks only about order and about which hardening items the first release needs.

## Decisions needed

1. Delivery order. Options:
   (a) Keep the current order: finish all of WL-P0-007, then 008 to 010, then the UI.
   (b) Thin slice first: after WL-P0-007C/L/D/E/F reach a working import on a synthetic instance, build WL-P0-011A/B/D and WL-P0-012A/B on a quote-free position read (holdings valued from the CSV's own market values), then add quotes, FX, crypto, exposure and exports.
   (c) Fix the shipped SQLite app first (UX-P1-008 to UX-P1-015) and continue V2 in the current order.
   Recommendation: (c) now, because those tickets are small and need no backend, plus (b) for V2 so the first end-to-end run happens before the largest tickets are built on it.
2. Hardening needed before the first invite-only release. Options:
   (a) Everything in r7 as approved.
   (b) Keep exactly-once booking, tenant isolation, stale-approval refusal and raw-byte cleanup in the first release. Move shared read/control rate buckets (WL-P0-007J) to P1 and document the open risk for instances that enable public registration.
   Recommendation: (b). The owner decides; r7 is an approved contract and only the owner can narrow it.
3. Whether WL-P0-008 may start once WL-P0-007D is merged instead of waiting for the whole WL-P0-007 epic. This is a hypothesis from the dependency graph, not a verified technical finding; an architect must confirm that position projection needs only the accepted-fact tables.
