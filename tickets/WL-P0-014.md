# WL-P0-014: Guide and verify the fresh-start move from the SQLite application to V2

## Goal

The owner decided on 2026-11-11 not to convert data from the shipped SQLite application. A V2 instance starts empty and the user imports their broker and exchange files again. The old instance stays exactly as it is, and the user opens it when they want to read an old report. This ticket makes that move safe and obvious: a guide, and a test that proves re-importing a sequence of files gives the expected result.

It replaces the earlier plan for a conversion tool with dry run, equivalence manifest and cutover commands. That tool is not built.

## Context

### Current behaviour

- The shipped application stores ledgers in SQLite workspaces and frozen report editions as files ([web-backups.md](../docs/web-backups.md), [web-adoption.md](../docs/web-adoption.md)).
- V2 stores canonical facts in PostgreSQL and does not keep imported files. A new account has one empty portfolio (WL-P0-005).
- WL-P0-021 delivers the V2 compose file on its own names, volume and port, so both applications can run on one machine. It also covers V2 backup and empty-target restore.
- V2 tracks a narrower scope than the old application: Bitcoin is purchases minus sales from imported exchange files, with no opening balance, wallet check or recorded cash flow ([PRODUCT_CONTEXT.md](PRODUCT_CONTEXT.md)). Totals in the two applications can therefore differ for the same person, by design.

### Expected behaviour

- A guide, "Moving from the earlier application to V2", linked from the README and the V2 first-run page, that tells a user in order:
  1. Leave the old instance running or stopped; nothing in it is changed or deleted.
  2. Start V2 (WL-P0-021) and create the account.
  3. Enable the sources and import files: for a broker, the holdings files they still have, oldest first, or only the latest if they do not care about history; for an exchange, one full order history file.
  4. What will look different and why: the scope differences above, one portfolio per user, no report editions.
  5. Where the old reports are: in the old application, unchanged.
  6. How to stop the old instance for good when they no longer need it, and how to keep its backup.
- The guide states what V2 does when an older holdings file is imported after a newer one, as the merged import reconciliation (WL-P0-007) behaves.
- [capability-status.md](../docs/capability-status.md) and the README say plainly that there is no automatic data migration.

### Scope

- In scope: the guide, the README and capability-status statements, a synthetic acceptance test, a check that the two compose projects do not collide.
- Out of scope: any conversion of SQLite data, serving old reports from V2 (WL-P0-020, now P2), retiring old import code (WL-P2-008), V2 backup and restore themselves (WL-P0-021).

### Implementation notes

- The acceptance test uses only the synthetic example files under `examples/data/` and synthetic variants of them with earlier dates. Never use or inspect a real workspace.
- Do not run both applications against one volume; the test asserts distinct project names, volumes and ports.
- Write the guide for a user, not an operator: no schema names or internal identifiers. Apply the repository's writing rules for documentation ([AGENTS.md](../AGENTS.md)).

## Acceptance criteria

- [ ] Given an empty V2 instance, when three synthetic holdings files dated in three different months are imported oldest first and then one synthetic order history file, then current positions equal the newest file, the value history has a point on each import date, and the Bitcoin quantity equals purchases minus sales in the order file.
- [ ] Given the same instance, when the oldest file is imported again, then the result matches what the guide says happens.
- [ ] Given the SQLite compose project and the V2 compose project started on one machine, then both answer on their own ports and neither writes to the other's volume.
- [ ] The guide lists every scope difference recorded in [PRODUCT_CONTEXT.md](PRODUCT_CONTEXT.md) that can change a total.
- [ ] The README and capability-status state that old data is not migrated and old reports stay in the old application.
- [ ] No step in the guide modifies, moves or deletes the old workspace.

### Tests

- An opt-in Docker test in the style of `tests/test_web_docker.py` for the import sequence and for the two compose projects.
